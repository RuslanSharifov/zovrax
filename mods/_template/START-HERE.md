# Zovrax — complete mod contribution starter

This folder is an **example, not a published mod**. The catalog builder deliberately ignores folders beginning with `_`, so `mods/_template/` will never appear on the site. A real contributor creates **their own named folder** under `mods/` and uses these files as a starting point.

## 1. Start a mod folder

Fork `RuslanSharifov/zovrax`. In the fork, create a branch and copy the starter:

```bash
git checkout -b add-my-mod
cp -R mods/_template mods/my-mod
```

Rename `my-mod` to your unique kebab-case slug (examples: `inventory-preview`, `better-hud`). Edit **every placeholder**, especially `slug`, `name`, `authors`, `source`, description, version and loader. New authors register in `site/data/catalog.json` under `developers` with a matching `id`. Mod folder names beginning with `_` are reserved for templates and not published.

## 2. Required and optional files

```text
mods/my-mod/
├── zovrax.json                 REQUIRED: catalog metadata, compatibility and release paths
├── ZOVRAX.md                   REQUIRED: public Markdown description, displayed in Overview
├── README.md                   Developer documentation: build, install, license, testing
├── ZOVRAX.ru.md                Optional Russian public description
├── ZOVRAX.fr.md                Optional French public description
├── assets/
│   ├── icon.svg                Example logo. Change or remove and update icon in JSON
│   └── preview.png             Optional screenshot (add real image before referencing)
├── releases/
│   ├── my-mod-1.0.0-fabric.jar  Real tested binary ONLY when released
│   └── my-mod-1.0.0-neoforge.jar
└── src/                        Actual mod source; add your loader's Gradle files at mod root
```

The `.jar` files in this tree are **illustrative names, not included files**. Don't create dummy JARs or list missing files in JSON. `assets/preview.png` is also illustrative and not included.

The source folder is **not** `site/data/mods/my-mod/`: that path is generated by the build. Never edit the generated `site/data/mods/<slug>.json` directly.

## 3. The manifest: `zovrax.json`

See the working [zovrax.json](zovrax.json) file alongside this guide. Only valid JSON is allowed: no comments, trailing commas or arbitrary field names.

| Field | Required? | How it is used |
| --- | --- | --- |
| `schemaVersion` | Yes | Number `2`, current schema. |
| `slug` | Yes | Lowercase kebab-case ID, **exactly the folder name**. |
| `name` | Yes | Displayed mod name, e.g. `Better HUD`. |
| `category` | Yes | Existing category ID from `site/data/catalog.json`: `hud`, `quality`, `gameplay`, `visual`, `utility`, `performance`. |
| `status` | Yes | `planned`, `development`, `released`, or `archived`. In current builder only `released` may have releases. |
| `featured` | Optional | Boolean; showcase suggestion. Keep `false` unless maintainer agrees. |
| `accent` | Optional | Theme accent, e.g. `lime`, `blue`, `purple`, `orange`, `teal`, `pink`. |
| `icon` | Optional | Relative icon file path, e.g. `assets/icon.svg`. Set `null` when absent. |
| `summary` | Yes | Multilingual short description object. At least `en` is required. `ru` and `fr` may be supplied; UI otherwise falls back to English. |
| `tags` | Optional | Array of search keywords. |
| `minecraftVersions` | Yes | Nonempty array, e.g. `["1.21.10"]`; target **Minecraft Java Edition** versions. |
| `loaders` | Yes | Nonempty array, e.g. `["Fabric"]`. Use actual loaders your code supports. |
| `authors` | Yes | Nonempty array of **developer IDs**, not arbitrary profile links. IDs must exist in the catalog's `developers` array. |
| `updatedAt` | Optional | ISO date such as `2026-11-11`, or `null` if not recorded. |
| `license` | Optional | Actual mod license, e.g. `MIT`, or `null` until declared. |
| `source` | Optional | HTTPS source repository or source-folder URL. Can be null for proprietary code. |
| `features` | Optional | Array of translated text objects `{"en":"...","ru":"...","fr":"..."}`. |
| `screenshots` | Optional | Image objects `{"src":"assets/preview.png","alt":{"en":"Screenshot"}}`. File must exist. |
| `releases` | Yes | `[]` when not released; real release objects only after tested JARs have been committed. |

### Metadata path rules

Local `icon`, `screenshots[].src`, Markdown image links and `releases[].downloads[].file` use paths **relative to the mod's folder**, not repository root or website root. No `../`, absolute paths or untrusted external binaries. Add the file to the folder before referencing it.

For the icon use `"icon":"assets/icon.svg"` only if `assets/icon.svg` exists; otherwise use `"icon":null`.

## 4. Public description vs. developer documentation

`ZOVRAX.md` is rendered in the public **Overview** tab. It can contain headings, lists, images, links, tables and fenced code blocks. The site sanitizes rendered Markdown before display. Relative image links are resolved to your mod's bundled assets.

- `ZOVRAX.md`: public description, English
- `ZOVRAX.ru.md`: public description, Russian (optional)
- `ZOVRAX.fr.md`: public description, French (optional)
- `README.md`: source/build documentation in GitHub, **not** the site description

Missing translations fall back to the English public description.

## 5. Releases and real one-click JAR downloads

**While developing or planning:** leave `"releases":[]` and keep `"status":"planned"` or `"development"`.

After real builds are compiled and tested, put them in `mods/my-mod/releases/`, update `"status":"released"`, and add versioned release objects. **`version` is the mod version; `minecraftVersions` is the Minecraft game version.** They are different.

```json
{
  "releases": [
    {
      "version": "1.0.0",
      "releasedAt": "2026-11-11",
      "minecraftVersions": ["1.21.10"],
      "loaders": ["Fabric", "NeoForge"],
      "changelog": {"en": "First tested release."},
      "downloads": [
        {
          "file": "releases/my-mod-1.0.0-fabric.jar",
          "label": "Fabric · Minecraft 1.21.10",
          "minecraftVersions": ["1.21.10"],
          "loaders": ["Fabric"]
        },
        {
          "file": "releases/my-mod-1.0.0-neoforge.jar",
          "label": "NeoForge · Minecraft 1.21.10",
          "minecraftVersions": ["1.21.10"],
          "loaders": ["NeoForge"]
        }
      ]
    }
  ]
}
```

This JSON is a **snippet** to paste into the manifest's `releases` field, **not a complete manifest**. These JAR names are only illustrative. For two or more mod releases, add more objects. Each file can override `minecraftVersions` and `loaders` to support exactly one loader/version combination. On the Zovrax download page players filter by **Minecraft version**, **loader**, and **mod release version**, then download the matching real `.jar` with one click.

The generator rejects missing files and files that don't begin with a ZIP/JAR signature, and computes SHA-256; this alone does not establish that a binary is safe or correct. All binaries require maintainer review. Do not add releases to a planned, development or archived mod.

## 6. Build, validate, and submit

From repository root (Node.js 22 recommended):

```bash
node .github/scripts/build-catalog.mjs
node .github/scripts/validate-catalog.mjs
python -m http.server 8000 --directory site
```

Open `http://localhost:8000/#/mods/my-mod` to preview your rendered description, card, icons, screenshots and downloads. Check desktop, mobile, translations and filter behavior. The build generates site JSON/assets in `site/data/`; add or edit the original `mods/my-mod/` source files, not generated output.

Push your branch to **your fork** and open a Pull Request against `RuslanSharifov/zovrax` → `main`. Automatic checks and maintainer approval are required; merging to `main` triggers GitHub Pages publication. Follow [CONTRIBUTING.md](../../CONTRIBUTING.md), [AGENTS.md](../../AGENTS.md), and [CHECKLIST.md](CHECKLIST.md).

### Important: authors and support links

The public developer card comes from `site/data/catalog.json`, not directly from `zovrax.json`. If your ID is missing, add a legitimate developer entry with `id`, `displayName`, optional GitHub username, avatar URL, social links and optional `support.kofi`. You must use only your own verified accounts and donation links.

### Rights and safety

Use code and art you have rights to publish. Never commit secrets, malware, spyware, counterfeit mod files or unlicensed Minecraft resources. The project is independent and not endorsed by Mojang or Microsoft.


## Free and premium publishing

Zovrax accepts **free**, **free + premium** and **premium-only** mod listings.
Premium downloads may be distributed by the developer through
[Lemon Squeezy](https://www.lemonsqueezy.com/) or another legitimate HTTPS store.
A premium-only listing does **not** need its proprietary source or paid JAR
inside the Zovrax repository. Only approved public listing metadata,
`ZOVRAX.md` and any permitted assets belong here.

Add `monetization` to `mods/<slug>/zovrax.json`:

```json
{
  "monetization": {
    "type": "free-premium",
    "premiumUrl": "https://your-store.lemonsqueezy.com/buy/your-product",
    "premiumLabel": "Get Premium"
  }
}
```

Allowed types: `free`, `free-premium`, `premium-only`.
For a **free** mod, set `premiumUrl` to `null`.
For a **premium-only** mod, use `"status": "released"` and `"releases": []`;
the site shows the external purchase button, not a fictional free download.
An optional `source` field may be `null` when source is proprietary.
The default remains `free`, so older listings continue to work.

The **Get Premium** action appears in the mod header only when a valid
premium URL is supplied. Developers may also link their external stores
from public Markdown or their own mod UI, but purchase actions must be
voluntary, clearly labeled and require user consent before opening a
browser. Zovrax does not handle payment, license keys, refunds or deliver
the premium binary. Developers must accurately represent ownership,
compatibility, dependencies and any included third-party assets.

## Sponsor and community features

- **Platform donations:** [Ko-fi](https://ko-fi.com/ruslansharifov)
  through [Zovrax Support](https://ruslansharifov.github.io/zovrax/#/support).
- **Creator donations:** Registered developers can specify their own
  `support.kofi` (optional). The official founder profile is explicitly
  marked with a Zovrax blue verification badge; regular GitHub users do not
  gain that badge automatically.
- **Accounts and statistics:** GitHub OAuth, cloud favorites, and aggregated
  per-mod stats have an optional Cloudflare Worker + D1 implementation
  under `community-worker/`. **They are not live until
  an operator configures OAuth, deploys the Worker and sets
  `site/config/community.json`.** Without it, favorites remain local
  in the browser and no fabricated global statistics appear.
